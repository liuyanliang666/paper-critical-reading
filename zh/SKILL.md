# 论文批判性精读

## 核心原则

读论文不是为了复述"作者做了什么"，而是为了搞清楚三件事：

1. 这个问题在什么条件下、为什么之前的方法解决不了
2. 作者的方案是被什么现实观察逼出来的，具体设计如何回应这个观察
3. 论文自己的实验有没有真正证明它的核心 claim，哪里可能是薄弱环节

如果输出只是把摘要复述一遍、或者把方法部分翻译一遍，就是没有完成这个任务。每一句分析都应该能追溯到论文里的具体依据，而不是泛泛的套话（比如"作者提出了一种新颖的方法""实验证明效果显著"这类话本身不构成分析）。

## 前置步骤：确保读的是全文，不是摘要

在生成分析之前，必须实际提取以下部分的内容：

- Method / Approach 部分的具体设计
- Experiments 部分的数据集、baseline、指标、消融实验
- Limitation / Future Work（如果论文里有明确写）

如果论文是 PDF，先完整提取全文文字（参考 pdf-reading skill 的做法），确认这几部分都读到了，再开始分析。如果论文过长、或者存在扫描版/公式图片无法提取文字的情况，如实告诉用户哪些部分没读到、可能影响哪部分分析的准确性，不要假装读过了硬编内容。

## 输出模板

ALWAYS use this exact structure（论文类型特殊时的调整见下文"特殊论文类型的调整"）：

```
## TL;DR
一句话：用什么方法解决了什么问题，效果如何

## 1. Task（形式化）
- 输入空间 / 输出空间是什么
- 目标函数或优化目标（用文本表达，不用 LaTeX，例如："loss = sum((y_i - f(x_i))^2)"）
- 评价指标是什么

## 2. Challenge
传统方法卡在哪、卡在什么机制上。要讲清楚"为什么"卡住，不能只说"效果不好"这种空话。

## 3. Method（中性描述，先不评价）
Pipeline 每一步做什么，用步骤列表或伪代码描述，作为后面 Insight/Novelty/Flaw 讨论的事实基础。

## 4. Insight & Novelty
对每一个 novelty，严格按这个格式描述：
【解决的问题是什么】->【受哪个 insight 启发】->【具体设计了什么，尽量具体】

每条 insight 都要说明来自什么 inspiration。如果论文原文没有明确写出 inspiration 的来源，必须在这条后面标注"（推测）"，不能编造论文没提过的动机。

## 5. Evidence & Validation
- 主实验是否真的支撑核心 claim
- 每个 novelty 是否有对应的 ablation 单独验证，还是只有整体效果对比
- 数据集/baseline 的选择是否可能存在有利于自己方法的情况

## 6. Potential Flaw
分三层，不要混在一起讲：
- 作者自己承认的局限（论文 Limitation/Future Work 里明确写的）
- 批判性发现的局限（论文没提，但从方法设计或实验设置能看出来的）
- 这些局限里，哪一个的 gap 大到值得单独写成一篇 paper，为什么

## 7. Motivation
用反问句还原作者可能是怎么想到这个 idea 的，遵循第一性原理：从问题本质出发去推导，而不是倒果为因地说"因为这样做效果好"。类似句式："之前的方法在 xx 情况下会失效，那能不能尝试 xx？"
```

## 硬性约束

- 不用 LaTeX，所有公式一律用纯文本表达式（例如用 `sum`、`^2`、`->` 这类记号）
- Insight/Novelty 部分：没有在论文中明确写出的 inspiration，一律标注"（推测）"；不能把 AI 自己的合理化解释包装成论文原文的说法
- 不要大段逐字引用论文原文——哪怕是用户自己上传的论文也一样，一律用自己的话转述；确实需要引用原句时，单句不超过 15 个词，且整篇分析里最多引用一次
- 只在对话中输出分析结果，不生成文件
- 省略客套话，直接进入分析，不需要在开头总结"这篇论文是关于……"这种前情提要

## 特殊论文类型的调整

- **理论证明类论文**（没有实验章节）：把"Evidence & Validation"改成审查证明是否严谨、假设是否现实、边界条件有没有被悄悄忽略
- **Survey / 综述类论文**：跳过 Task 的单一形式化，改成总结这个领域的问题分类方式；Novelty 部分改为评价这篇综述的分类体系或视角有什么新意，而不是找一个具体的技术创新点
- **System 类论文**（强调工程实现而非算法创新）：Method 部分要更细致地拆解系统架构和组件间的交互；Evidence 部分重点看性能/成本 benchmark 是不是在真实场景、真实负载下测的，而不是理想化的 micro-benchmark

## 触发时机

满足下列任一条件就应该主动使用这个流程，不需要用户明确点名这个 skill：

- 用户上传了论文 PDF，并提出任何形式的"讲讲/分析/解读/总结/精读"要求
- 用户提到"这篇论文""这篇 paper""帮我读一下"等，同时附带了论文文件或链接
